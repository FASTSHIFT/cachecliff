# cachecliff — STM32H743 与 i.MX RT1176 的对比

日期：2026-11-02
状态：两块板子上的实测。两边都是 Cortex-M7，同一份回调库（`ebc8ae01`，1024 个回调），同样的完整扫描（`CC_QUICK=0`）。
对比用**周期**（`ccreport.py --cycles`），因为主频差了 6.6 倍。

[`examples/h743-vs-rt1176.md`](examples/h743-vs-rt1176.md) 是 `tools/ccreport.py` 生成的完整报告（三条曲线：H743、RT1176 从 RAM、RT1176 从 QSPI Flash），
这一篇只写读数和结论。§1 到 §3 是前两条，§5 是第三条。

## 1. 配置

| | STM32H743 | i.MX RT1176（MIMXRT1170-EVK） |
|---|---|---|
| 主频 | 150 MHz | 996 MHz |
| 缓存 | I-cache 16 KiB，D-cache 16 KiB | I-cache 32 KiB，D-cache 32 KiB |
| 代码在 | 内部 Flash | OCRAM1（调试器装载到 RAM 里跑） |
| 数据区 | AXI SRAM 256 KiB | OCRAM2 256 KiB |
| D-cache 策略 | 写回，写分配（ARMv7-M 默认内存映射，没配 MPU） | 写回，不分配写（`BOARD_ConfigMPU`） |
| 计时 | DWT_CYCCNT | DWT_CYCCNT |

两块板子的代码不在同一种存储里：H743 从 Flash 取指，RT1176 从 RAM 取指。这是各自当前能用的配置
（RT1176 的 RAM 版先测，Flash 版在 §5），所以下面比的是“这两个系统”，不是纯内核差异。

## 2. 读数（周期）

| | STM32H743 | RT1176 |
|---|---|---|
| 热参考（16 个回调） | 162 周期/次 | 161 周期/次 |
| 代码拐点（热参考的 125% 以内） | 14 KiB | 29 KiB |
| 1024 个回调（459 KiB） | 309 周期/次（1.90x） | 706 周期/次（4.37x） |
| 数据读延迟，D-cache 命中 | 3 周期 | 3 周期 |
| 数据读延迟，缓存之外 | 11.9 周期（80 ns） | 41 周期（41 ns） |
| 最大数据区（256 KiB）上的 16 个回调 | 1.35x | 2.18x |
| 随机顺序对重复序列的差 | 41.5 周期/次 | 28.5 周期/次 |
| 倾斜度（skew 8 对均匀） | 1.14x（更慢） | 0.88x（更快） |

## 3. 结论

- **内核一样，热循环就一样。** 热参考两边都是 161 到 162 周期/次，D-cache 命中的依赖读都是 3 周期。差别全在缓存**之外**。
- **拐点跟缓存大小对得上。** I-cache 16 KiB 的 H743 在 14 到 28 KiB 之间起跳，32 KiB 的 RT1176 在 29 到 57 KiB 之间起跳。
  D-cache 的数据拐点也一样：16 到 32 KiB 对 32 到 64 KiB。
- **RT1176 的缺失代价按周期算高得多。** 超出 I-cache 之后，1024 个回调比热参考多出 545 周期/次，H743 只多 147。
  RT1176 的核跑在 996 MHz，一次缺失要等核外的 RAM，折合成核周期就是几十个；H743 的核慢得多，同样的等待折合成的周期少。
- **按时间算则反过来。** 缓存外的依赖读 RT1176 是 41 ns，H743 是 80 ns：RT1176 的片上 RAM 本身更快，只是核更快得更多。
  所以“同样的缓存命中率”在两块板子上换算成时间的差别很大，也说明 CoreMark 这类全部命中缓存的跑分测不出这一点。
- **倾斜度的符号不同。** H743 上更集中反而更慢（多一次抽样的开销盖过了好处），RT1176 上更快：缺失贵到热点子集的收益盖过了抽样开销。

## 4. 局限

- §1 到 §3 里代码所在存储不同（Flash 对 RAM），不是对等比较；RT1176 的 Flash 版见 §5。
- RT1176 一侧只有程序自己的计时，没有 ETM trace 对拍；H743 一侧已对拍（见 `04-validation-stm32h743.md`）。
- 每块板子只测了一次。
- RAM 版是用调试器装载的，不经过板上的 Flash 启动流程。RT1176 的串口输出在这块板上读不出正确字符（原因没查清），
  两个版本的报告都是从目标内存的日志缓冲区读出来的，见 `02-porting.md`。

## 5. RT1176 从 QSPI Flash 取指（XIP）

代码放在 QSPI NOR（0x30000000）里原地执行，经 32 KiB I-cache 取指，和 LVGL 演示的 Debug 配置一样；数据区仍在 OCRAM2。
烧录是先把 SW1 拨到 Serial Downloader，用 pyocd 烧，再拨回 QSPI 启动（开关的位置见 `lv_port_nxp_evkmimxrt1170/cachecliff_port/README.md`）。
Flash 配置是工程自带的 FCB：QSPI 四线 SDR（`0xEB` Quad I/O 读），SCK 132 MHz（SYS_PLL2 528 MHz 四分频），峰值带宽 66 MB/s。
（FCB 源码里的注释写着 DDR，但读序列用的是 SDR 指令，`controllerMiscOption` 的 0x10 是 safe-config 位，不是 DDR 位。）

| | RT1176 从 OCRAM | RT1176 从 QSPI Flash |
|---|---|---|
| 热参考（16 个回调） | 161 周期/次 | 162 周期/次 |
| 代码拐点 | 29 KiB | 14 KiB |
| 64 个回调（29 KiB） | 179（1.10x） | 1271（7.85x） |
| 128 个回调（57 KiB） | 368（2.27x） | 6097（37.7x） |
| 1024 个回调（459 KiB） | 706（4.37x） | 10201（63.0x） |
| 数据读延迟（缓存内 / 缓存外） | 3 / 41 周期 | 3 / 41 周期 |
| 随机顺序对重复序列 | 28.5 周期/次 | 1111 周期/次（7.5x） |

- **代码在缓存里时，Flash 和 RAM 没有区别**：16 个回调以内两边都是 160 周期左右。
- **代码一超出缓存，Flash 的代价高一个数量级。** 1024 个回调时每次调用要 10.2 µs，是 RAM 版的 14 倍，是热参考的 63 倍。
  对比 H743 的 1.9 倍：H743 的内部 Flash 一次读 256 位，核的主频又低得多，同样的缺失折合成周期少得多。
- **拐点提前了一半。** Flash 版的拐点在 14 KiB，RAM 版在 29 KiB。64 个回调（29 KiB）的代码本身装得进 32 KiB 的 I-cache，
  但回调里的常数读（字面量池，见 `04-validation-stm32h743.md` §3）也要走 Flash 和 D-cache，我推测是两边合起来装不下（没有用 trace 验证）；
  RAM 版里同样的缺失便宜得多，看不出来。
- **预测失败的“代价”被缓存缺失放大了**：64 个回调随机顺序比每 32 次重复的序列慢 7.5 倍，这里差的主要是缓存命中，不是分支预测。
- **数据一侧两个版本完全一致**（3 和 41 周期，热参考 162 对 162），可以当作这块板子两次测量的重复性检查。
- 缺失代价是由工程的 Flash 配置决定的，结论是“在这份配置下”。Flash 一次行填充的延迟见 §6。

## 6. QSPI Flash 的延迟和带宽

问题：能不能直接用 Flash 带宽估算一次缓存行填充的延迟？不能，带宽只给出传输那一段。

用 `lv_port_nxp_evkmimxrt1170/cachecliff_port/latency/lat.py` 直接测。它把一段依赖读循环装进 ITCM，用调试器在正在运行的核上跑，
每次读的地址都依赖上一次读到的值，所以每次读的时间就是延迟；结束后恢复寄存器和 ITCM。D-cache 开，区域 4 MiB 远大于缓存。

| 访问 | 周期/次 | 折算 |
|---|---|---|
| 随机读 OCRAM2 4 KiB（全命中，即循环本身） | 12.3 | 命中 3 周期，其余是循环 |
| 随机读 OCRAM2 512 KiB | 49.2 | 一次行填充约 40 周期（40 ns） |
| 随机读 QSPI Flash 4 MiB | 885.0 | 一次行填充约 876 周期（**879 ns**） |
| 顺序读 QSPI Flash，32 字节步长 | 485.3 | 一行约 476 周期（478 ns），**67 MB/s** |

（周期是 996 MHz 核的周期；扣除循环本身 9 个周期；两次重复测量一致。）

**带宽只解释了顺序读。** 顺序读 32 字节一行 478 ns，换成带宽是 67 MB/s，是 SCK 132 MHz × 4 线 = 66 MB/s 的 100%，
所以顺序读是纯带宽受限，FlexSPI 没有额外空隙。但随机读一行要 879 ns，比 32 字节的传输时间（485 ns）多出 394 ns，
这部分是每次随机访问都要付的固定开销，带宽里看不到。

**按 FCB 的读序列可以估到差不多。** 读序列是：命令 `0xEB`（1 线，8 个 SCK）+ 地址 24 位（4 线，6 个 SCK）+ 空周期 9 个 + 数据 32 字节（4 线，64 个 SCK），
共 87 个 SCK，132 MHz 下是 659 ns；再加 FlexSPI 的片选建立/保持（`FLSHCR1` 里 TCSS=3、TCSH=3，共 6 个 SCK，45 ns）约 704 ns。
实测 879 ns，比这个估算高 175 ns（25%）。多出的部分（约 23 个 SCK）不在 LUT 里，应该是片选高电平的最短时间、核与 FlexSPI 之间总线的跨时钟域和采样延迟，
我没有把它们逐项拆开。

所以估算的办法是：

```
延迟 ≈ (命令 + 地址 + 空周期的 SCK 数) / f_SCK  +  行字节数 / 带宽  +  固定的片选和总线开销（实测约 0.2 µs）
      = 23 / 132 MHz            +   32 B / 66 MB/s   +   ~0.2 µs
      ≈ 174 ns + 485 ns + ~220 ns ≈ 880 ns
```

前两项可以从 FCB 和时钟算出来；第三项要测一次。

和 §5 对起来：1024 个回调时每次调用 10201 周期，按 876 周期一次的随机行填充折算，相当于每次调用约 11.6 次缺失；
64 个回调时多出的 1110 周期相当于约 1.3 次。
