# cachecliff — 设计

## 1. 要解决的问题

CoreMark 之类的小 benchmark 能整个装进任何现代内核的缓存：CoreMark 的内核只有几 KB 代码，数据放在 TCM 里，
测到的是流水线，不是存储系统。真实程序的代码比指令缓存大，数据比数据缓存大，跑出来比跑分慢得多
（同一块 STM32H743 上，CoreMark 关 D-cache 速度不变，LVGL 一帧慢 1.35 到 1.8 倍）。

cachecliff 不求给出一个分数，而是**画曲线**：每次只改变一个量，看耗时在哪里突然变陡（悬崖），悬崖的位置就是缓存或存储层次的边界。

## 2. 为什么是"预生成的库 + 运行时旋钮"

缓存只看见**被执行**的代码，而不是链接进来的代码。所以代码足迹不能用宏来调（那样每个点要重编一次，而且链接进来的未执行代码什么都不测）。
cachecliff 的做法：

- 一个**库**（bank）：1024 个互不相同的回调函数，已生成并提交在 `bank/` 下，构建时不需要 Python。
- 运行时参数决定**调用哪些**：从前 n 个里挑，n 取 4、8、…、1024，一个构建扫完所有点。
- 宏只决定容量（`CC_NFUNCS`、`CC_DATA_BYTES`），让程序装得进小目标。

没有选的方案：要求用户先跑生成器（门槛高）；用预处理器重复展开代码（编译慢、不可控、结果依赖编译器怎么折叠）。

## 3. 回调

签名 `uint32_t cc_fNNNN(uint32_t x, cc_ctx *c)`，`x` 在回调之间传递（形成数据相关链，防止被编译器丢弃或并行化），
`c` 指向数据区。每个函数是一段直线代码，语句从下面几类里按权重抽（`--mix` 可改）：

| 类 | 内容 |
|---|---|
| `alu1`/`alu2`/`alu3` | 移位、异或、加常数等 |
| `mul` | 乘一个奇数 |
| `ld1`/`ld2` | 在数据相关的地址读数据区（`ld2` 先移位，地址更分散） |
| `st` | 在数据相关的地址写数据区 |
| `brr` | 很少成立的条件分支（可预测） |
| `brh` | 两边各约一半的条件分支（难预测） |
| `loop` | 2 到 6 次的小循环 |

函数之间常数、语句顺序、语句数都不同，所以不共享代码。每个函数 6 到 64 条语句（`--sizes` 可改），约 100 到 400 字节代码。

### 3.1 均衡的大小

大小是**均衡**排列的：每 64 个函数里各种大小出现的次数相同，并且前 2、4、8、… 个函数的平均大小都接近总体平均。
没有这一条，只扫前几个函数时，几个特别大或特别小的函数会让"每次调用的工作量"本身变化，曲线里混进了不是缓存造成的台阶。
这是看到第一版里热参考偏斜之后加的。

### 3.2 校验

生成器用 Python 另写了一份语句的实现，算出：

- 依次调用前 64、128、… 个回调各一次的返回值；
- 在前 64 个里随机调用 2000 次的返回值。

程序启动时用这些值校验链接进来的回调（`validation: ok`），和 CoreMark 校验 CRC 是一回事：编译器或内核算错了，数字就不值得看。
库的指纹（`bank ebc8ae01`）打印在报告头里，用来区分不同的库。

## 4. 调度器

`cc_run(cfg, calls, seed, x0)` 用 xorshift32 产生随机数，乘移位映射到 `[0, n)` 选回调，通过函数指针表间接调用。四个旋钮：

| 旋钮 | 含义 |
|---|---|
| `nfuncs` | 从前 n 个回调里挑（代码足迹） |
| `skew` | 1 为均匀；k 为 k 次抽样取最小值，k 越大越集中在前面的少数函数（热点子集） |
| `period` | 调用序列每 period 次重复一遍；0 为不重复（间接分支的可预测性） |
| `data_bytes` | 回调使用的数据区大小（数据足迹） |

调度器本身（抽样、取表、间接调用）的周期算在每次调用里。

`skew` 每加 1 就多一次抽样，实测在 Cortex-M7 上每次约 7 到 8 个周期。库很大、热点子集仍装不进缓存时，这个开销会盖过热点带来的好处，
倾斜度一节就会出现"越集中越慢"（STM32H743 上 skew 8 是均匀的 1.15 倍）。这是这个旋钮的已知局限，读那一节时要把它算进去。

## 5. 测量

`cc_measure()`：

1. 试跑 256 次、1024 次、…（每次 ×4），直到耗时达到目标的 1/8；
2. 按比例算出耗时约 20 ms（`CC_TARGET_MS`）所需的调用数；
3. 预热一遍（这时才可能校正调用数）；
4. 计时 3 次，取**中位数**。

计时器要求是自由运行的 32 位计数器；引擎把每段间隔控制在 2^31 个 tick 以内，所以 32 位回绕不影响结果。
`--quick` 把每点的时间缩到 1/4。

### 5.1 指针追逐

回调测的是"一次调用的总耗时"，混着发射、分支、缓存。要直接读缓存延迟，用**指针追逐**：

- 数据区切成 64 字节的节点，用 Sattolo 洗牌连成一个随机的单环（一圈遍历所有节点）；
- 每次读取的地址来自上一次读取的结果，所以读之间不能重叠，每次读的耗时就是延迟；
- 循环通过 `volatile` 指针读，防止优化器把没有副作用的循环整个删掉（实际发生过：-O2 下循环被删，耗时是 0；
  假计时器的单元测试发现不了，所以另有用真实时钟的 `tests/test_hosted.c`）。

## 6. 报告和"拐点"

报告分四节：代码足迹、数据足迹（指针追逐和回调各一列）、倾斜度、可预测性。热参考是 16 个回调、4 KiB 数据。
末尾的 summary 给出**拐点**：耗时不超过热参考 125% 的最大足迹。代码用回调占的字节数（由函数地址之差得到，
所以要求编译器按生成顺序放函数），数据用指针追逐的结果。

## 7. 边界

- cachecliff 测的是"这个编译器、这个内核、这些链接选项"下的数字，不是内核的固有属性。例如在 Cortex-M 上，
  回调里的 32 位常数默认放在字面量池里经 D-cache 读，代码足迹扫描就混进了 D-cache（见 `04-validation-stm32h743.md`）。
- 数据区越大，追逐的建环时间越长；这部分不计入每次读的耗时，但会计入函数的总耗时。
- 随机序列下，分支预测器对 `brh` 的影响也在曲线里；要单独看它，用可预测性那一节。
